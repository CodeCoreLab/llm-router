LLM Router

接多个 LLM 供应商是常态，而接入方要重踩的坑也是常态： 主力模型限流、兜底端点抖动、推理模型返回空内容、JSON 输出不受约束。

  • 候选路由：P1→P12 按优先级遍历，硬错快跳、瞬错退避，判死端点熔断冷却。
  • 多 key 轮换：单端点挂一列 key，429/403 自动切下一把，端点不掉链。

产品概览

把「每个接入方都要重踩的坑」收敛成一个模块

对接 LLM 供应商的工程问题高度重复：多供应商降级、限流轮换、推理型模型 的空响应、JSON 输出约束、外层超时失控。这些问题在监控分析、告警解读、 报告生成等每个接入点都会再出现一次——每次重写一遍重试与降级，就多一份分叉的维护成本。

  • 路由可声明：端点、优先级、多 key 池全部落在一份 YAML，代码零硬编码。
  • 失败可降级：硬错快跳、瞬错退避、熔断冷却，全链路只影响当次调用。
  • 输出可约束：强制 tool calling 绑定 JSON Schema，结果可直接进下游程序。

模块只有 llm_router.py 一个文件。调用方 from llm_router import call_llm 之后，候选构造、路由排序、重试降级、结果校验全部在函数内部完成——返回 str 或 None，不抛网络异常，调用方不需要理解降级链。

配置优先级为 YAML > 环境变量 > env 文件。密钥一律经 ${VAR} 插值注入，配置文件本身不含明文凭据；诊断接口 list_endpoints() 输出的 key 视图自动脱敏。

所有状态（熔断计时、延迟采样、缓存）均为进程内态，无外部依赖、无守护进程；单进程部署不需要任何协调，多进程部署各自治愈。

主力限流 → 429 自动轮换同端点下一把 key，再切下一候选
端点抖动 → 硬错快跳熔断，恢复后按实测延迟重排健康端点
空响应 → 推理预算耗尽自动放大 max_tokens 重试一次
JSON 失控 → tool_choice 强制单函数，arguments 即合法 JSON
超时失控 → deadline 预算闸，内层重试永不跨越外层硬约束
重复付费 → 进程内 TTL 缓存，同 prompt 不重复请求

候选路由

P1→P12 按优先级遍历。连接错与 401/403/404 视为硬错立即切下一家；超时、429、5xx 视为瞬错，单端点指数退避重试后再切换。

核心功能

四项核心能力，实现细节均可追溯

以下能力的实现要点均取自实际源码，涵盖关键参数与边界处理， 不涉及概念性描述，便于逐项核验。

  • 多 key 轮换：单端点一列 key，429/403 轮换，端点不掉链。
  • 推理预算：预算耗尽放大重试一次，上限可配防单请求失控。
  • deadline 闸：外层超时是硬约束，内层重试不得跨越。
  • 拒答检测：拒答前缀与措辞识别，计入重试不返回半成品。

多 key 轮换

限流轮换 key，故障轮换端点——两种降级互不误伤

1api_key 支持列表一个 endpoint 配 N 把 key，构造候选时展开为 P1-k1…P1-kN，URL+MODEL+KEY 三元组去重。
2429 是 key 的事，不是端点的事触发限流时对端点 _mark_good——端点还活着，只是这把 key 被限；切下一候选即切下一把 key。
3401/403 是端点的事鉴权错直接 _mark_dead 熔断整段冷却，不再对同端点浪费重试预算。
4环境变量同构LLM_P{n}_KEY1..KEY9 索引式多 key 池，与 YAML 行为一致，无 YAML 依赖时可用。

推理预算治理

思考链不是答案——空 content 的根因治理

1识别「预算耗尽」特征finish_reason=length 且 reasoning_tokens ≈ completion_tokens 时，content 必为空——这不是端点故障，不该熔断。
2一步放大，不逐级试探直接提到 CEILING（默认 16000）重试一次。「小预算逐级放大」实测把单次调用拖到 90~141s，远超自动化可接受延迟。
3放大后同步放宽超时思考链越长生成越久，沿用原 timeout 会读超时；最小超时可配（默认 180s）。
4reasoning 永不冒充答案重试仍空则返回空 content，由调用方判「无答案」降级——绝不把思考过程当结果返回。
# 外层只给 60s：内层重试不得跨越这条线
deadline = time.monotonic() + 60

try:
    text = call_llm("……", deadline=deadline)
except LLMDeadlineExceeded:
    text = "(LLM 超时，走规则兜底)"  # 确定性兜底

# 每次尝试前：eff_timeout = min(timeout, 剩余预算)
# 剩余 ≤ 1s → 立即上抛，不再切候选
# 没有 deadline 闸：外部 SIGKILL 会跳过兜底逻辑
deadline 预算闸

外层超时是硬约束，内层重试不得跨越

1问题：兜底永远执行不到外层任务被 SIGKILL 后，调用方的降级逻辑（规则引擎、缓存回退）永远不会运行——内层再怎么重试都是徒劳。
2预算闸语义每次尝试前检查剩余预算：不足 1s 直接抛 LLMDeadlineExceeded；充足则把单次 timeout 收敛为 min(timeout, 剩余)。
3异常即协议预算耗尽以异常显式上抛，调用方在 except 分支走确定性兜底——降级路径是代码，不是巧合。

结构化输出

约束放在协议层，不放在提示词里祈祷

1response_format 不可靠推理型端点上 json_object 18.8s 后 finish=length、content 为空——推理 token 把预算吃光，对 JSON 无任何约束力；json_schema 被部分上游直接 400。
2tool calling 强制单函数把 schema 包成唯一 function，模型必须以合法 JSON 调用它；实测 1.5s 返回 94 completion tokens 的合法 arguments。
3失败返回 None 不抛异常无 tool_call、arguments 非法 JSON、全部候选失败——统一返回 None，调用方自行降级，解析路径不碎裂。
4与降级链天然协同上游不支持 tools 会返回普通文本，被判为失败自动切下一候选——结构化能力也成为候选排序的一部分。
路由管线

五段单向管线，每次调用走完整条链

从配置到返回，数据单向流动：每一段只依赖上游产物，任何一段失败 都以「跳过或上抛」收场，不产生半成品结果。

  • 可测试：五段均为纯函数或近纯函数，36 项测试全部离线 mock 完成。
  • 可观测：结构化 JSON 日志开关，命中端点、延迟、缓存命中均可留痕。
  • 可诊断：list_endpoints() 随时导出当前候选链（key 自动脱敏）。

失败路径全覆盖

配置缺失返回 None 并告警，不打断调用方；空响应切候选不熔断（避免污染熔断计数器）；拒答文本计入重试耗尽后放弃——三类「软失败」与硬错、瞬错严格区分，各自的处置互不误伤。

进程内状态机

熔断计时、延迟采样、key 索引、TTL 缓存全部为进程内状态，读写均有锁保护（读-改-写整段持锁，杜绝并发覆盖）。无外部存储、无守护线程，单进程即完整运行时。

对比基准

裸写 requests，每类失败都要自己踩一遍

对比基准为「直接 requests.post + 手写 try/except」这一常见做法， 而非虚构竞品；以下逐项说明差异与实现方式。

熔断状态机

裸写方案对死端点照样发起请求，每个调用都吃满超时。llm-router 判死后冷却窗口内直接跳过，窗口过后自动恢复探测。

skip = now < dead_until ︱ cooldown = 300s
死端点零探测成本

凭据边界

裸写方案常把 key 写进配置或代码。llm-router 的 key 只存在于环境变量与内存，YAML 用 ${VAR} 占位，诊断视图露头尾不露全量。

key_view = head(8) + "..." + tail(4)
配置与日志零明文

Prompt 缓存

监控分析、报告生成类任务常以相同 prompt 反复调用。进程内 TTL 缓存（默认 300s，上限 500 条）让重复分析不重复付费。

cache_key = sha256( model ‖ system ‖ prompt )
TTL 300s · 超限清最老 100 条

拒答防线

上游返回"I'm sorry / [advisor]"类拒答文本时，裸写方案会把它当正常结果透传。llm-router 识别拒答计入重试，耗尽后切下一候选。

refusal = prefix Match ∨ phrase ∈ head(400)

2基础调用

text = call_llm("总结异常")            # 按优先级

print(list_endpoints())
